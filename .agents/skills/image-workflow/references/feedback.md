# 用户反馈的保存与人工应用

收到 comment、记录用户验收或准备读取历史规则时使用。当前仅有模板及人工索引约定；自动候选检索、自动索引维护／重建属于架构第 3 步，尚未实现。不要编造相关命令或声称已经自动召回。

## 收到评论时

1. 在对应任务 feedback.md 追加原话、时间、被评论的准确图片版本和位置。先核对评论对象；无法确定且会影响修改时记录待澄清，不把它随意绑定到最新图。
2. 分别保存用户原话、Codex 的理解与已实际采取动作，不将推断改写成用户要求。按具体版本记录待验收／需修改／通过；评论存在不等于接受。
3. 可复用意见用 rule 模板写到仓库根 review_knowledge/rules/，注明来源、适用项目／角色／版本、检查动作、状态与例外；无明确范围先限于本任务。不要为尚无真实反馈的仓库编造规则。
4. 人工追加或更新 review_knowledge/index.md 的定位条目。原话留在任务内，规则正文单独保存，索引只保留检索维度和链接。旧规则被替代时保留历史与关联。
5. 简述记录了什么、哪些规则已更新、哪些仍待澄清。收到评论本身不启动生成；新批次须有用户明确要求。

每条评论都保存，不是每条都必须提炼为长期规则。一次构图偏好不能自动推广成全局约束；某图的创作例外不删除通用规则。反馈可校准用户偏好、错误检查与验收要求，但不自动成为官方角色事实，也不是对模型参数进行训练。

## 当前怎样找历史依据

先读当前任务已有反馈，再人工查看索引，完整读取适用的通用规则和同角色／版本规则，不依赖相似度排名或案例数量上限。按动作、道具、构图、文字、缺陷类型补查相关案例；自动化尚未实现时如实记录人工查找范围。

回到原始 comment 核对范围；涉及视觉关系时看对应图片，必要时看前后版本。图片不可用时不能将未能核验的视觉解释写成确定规则；明确的文字偏好可以按其原意应用。分别判断采用／不适用／冲突待解决，并在本轮 prompt 或 review 中记录采用的规则／反馈编号及版本、用途。

其他角色案例只可迁移适用的通用作画经验，不能迁移角色设定。资料范围限于已授权项目；其他项目的接口调查材料不进入反馈案例库。当前用户指令与历史规则冲突时遵从当前明确指令，记录本次例外；事实冲突需要核对参考资料，不能为了统一规则而捏造设定。

生成后若出现此前未涉及的新缺陷，按该缺陷再人工补查相关案例，指导本轮判断或下一轮改法。以后规则变化不追改过去的监修结论；后续真实任务才能验证同类错误或误判是否减少，不能仅凭规则已经保存宣称效果提升。
